CZĘŚĆ A — kryteria oceny

Jak projekt realizuje 5 kryteriów

Każde kryterium pokazane na poziomie całego pakietu, z konkretnymi przykładami z kodu.

1

Definiowanie kryteriów akceptacji

Każdy test = jeden mierzalny warunek z kontraktu, zapisany jako Akcja → Oczekiwane i otagowany kategorią.

T-082 Adding a bearer above the valid range is rejected
    [Documentation]  Akcja: dodanie bearera o ID = 10 (powyżej zakresu 1-9).
    ...              Oczekiwane: błąd 422 — bearer ID musi być z dozwolonego zakresu.
    [Tags]    add-bearer    validation    boundary

Kryterium słowne → postać mierzalna: status >= 400 + body zawiera „Input should be less than or equal to 9”. Tagami (robot -i validation) można uruchamiać wybrane klasy kryteriów.

2

Automatyzacja wg kryteriów

Keyword-driven DSL z argumentami w nazwie (BDD) — testy czyta się jak zdania:

Add bearer 1 to UE 50
Stopping traffic on UE 77 bearer 9
   should be rejected with message "UE not found"
  • Warstwy: akcje / asercje domenowe / helpery.
  • Suite Setup: sesja HTTP; Test Setup → /reset: izolacja.
  • Dane w *** Variables *** — łatwa zmiana.
  • expected_status=any — kontrola asercji na błąd.
  • Wzorzec Arrange–Act–Assert w każdym teście.

✔ Testy deterministyczne, niezależne od kolejności, odporne na zmianę danych.

3

Odczyt raportów i wnioski

67 / 13

pass / fail (80)

report.html — podsumowanie i podział wg tagów; log.html — każdy krok z żądaniem i odpowiedzią; output.xml — dane maszynowe (CI).

Wniosek: 13 FAIL to nie awaria środowiska — to realne defekty aplikacji. Potwierdzone powtarzalnością (ten sam wynik przy ponownym uruchomieniu).

Konkluzja: czerwony wynik = informacja, nie porażka. Kluczowe jest ustalenie, czy zawinił test, czy system.

TESTY NOK — wykryte defekty

13 testów NOK — szczegóły

Każdy z poniższych testów celowo pada, bo ujawnia defekt aplikacji. Format każdego slajdu: Oczekiwane → Otrzymano → Defekt.

Rozkład: Attach 2 · Check Transfer 5 · Delete Bearer 1 · Stop Transfer 2 · Transfer 3

T-059
Attach UE With ID 0 From Spec Range Succeeds
attach.robot · obszar: attach / boundary
Oczekiwane: HTTP 200 — wg specyfikacji zakres UE to 0–100, więc UE o ID 0 powinien zostać przyjęty.
Otrzymano: HTTP 422 — API odrzuca UE o ID 0.
Defekt: błędnie obsłużona dolna granica zakresu — wartość 0 jest traktowana jako nieprawidłowa, mimo że mieści się w kontrakcie.
T-077
Attach With Boolean True As ue_id Is Rejected
attach.robot · obszar: attach / walidacja typów
Oczekiwane: HTTP 422 — wartość logiczna true nie jest poprawnym identyfikatorem; ue_id przyjmuje wyłącznie liczby całkowite.
Otrzymano: HTTP 200 — API akceptuje true i tworzy UE.
Defekt: brak walidacji typu — Pydantic po cichu rzutuje true na liczbę 1. (odpowiednik regresji BUG-4)
T-027
Aggregated traffic with default unit returns values in kbps
check_transfer.robot · obszar: statystyki
Oczekiwane: domyślną jednostką wg spec jest kbps — odpowiedź powinna raportować wartości w kbps (klucz total_tx_kbps).
Otrzymano: brak klucza total_tx_kbps w odpowiedzi.
Defekt: domyślna jednostka kbps nie jest raportowana zgodnie ze specyfikacją.
T-028
Traffic of a single inactive bearer is rejected
check_transfer.robot · obszar: walidacja
Oczekiwane: błąd — sprawdzenie transferu bearera, który nigdy nie został ustanowiony (bearer 5), powinno zostać odrzucone.
Otrzymano: HTTP 200 — API zwraca dane dla nieustanowionego bearera.
Defekt: brak walidacji istnienia bearera przy odczycie transferu.
T-029
Existing bearer with no transfer history is rejected
check_transfer.robot · obszar: walidacja
Oczekiwane: HTTP 404 — bearer 9 istnieje, ale nigdy nie miał sesji transferu, więc brak historii powinien dać błąd.
Otrzymano: HTTP 200 — API zwraca puste statystyki zamiast błędu.
Defekt: brak rozróżnienia „brak historii transferu” od „aktywna sesja”.
T-078
bearer_count reflects all configured bearers, not only active
check_transfer.robot · obszar: statystyki
Oczekiwane: bearer_count = 2 — pole powinno zliczać skonfigurowane bearery (domyślny 9 + dodany dedykowany).
Otrzymano: bearer_count = 0 — pole liczy tylko aktywne sesje transferu.
Defekt: zła semantyka pola — liczy aktywne transfery zamiast skonfigurowanych bearerów. (odpowiednik BUG-5)
T-079
Duration resets to zero when traffic is restarted
check_transfer.robot · obszar: statystyki / czas
Oczekiwane: duration < 2s — po ponownym starcie na tym samym bearerze czas powinien być resetowany i mierzyć tylko bieżącą sesję.
Otrzymano: duration ≈ 3s — czas akumuluje się między sesjami.
Defekt: duration sumuje czas poprzednich sesji zamiast resetować się przy starcie. (odpowiednik BUG-10)
T-067
Deleting a bearer with an active transfer is rejected
delete_bearer.robot · obszar: integralność stanu
Oczekiwane: błąd — nie można usunąć bearera z aktywną sesją; transfer trzeba najpierw zatrzymać.
Otrzymano: HTTP 200 — API usuwa bearer mimo trwającego transferu.
Defekt: brak ochrony przed usunięciem zasobu będącego w użyciu. (odpowiednik BUG-8)
T-035
Stopping traffic for all bearers of a UE returns success
stop_transfer.robot · obszar: spec ↔ implementacja
Oczekiwane: HTTP 200 — wg dokumentacji EPC (pkt 5) transfer można zakończyć dla wszystkich bearerów, bearer ID jest opcjonalny: DELETE /ues/{id}/traffic.
Otrzymano: HTTP 404 — endpoint masowego stop nie istnieje w API.
Defekt: brak zaimplementowanej funkcji wymaganej przez specyfikację — luka implementacja ↔ kontrakt.
T-036
Stopping traffic clears the transfer statistics
stop_transfer.robot · obszar: czyszczenie stanu
Oczekiwane: po zatrzymaniu transferu pola protocol i target_bps powinny być null — dane poprzedniej sesji nie mają być widoczne.
Otrzymano: protocol = "tcp" — stare dane pozostają po stopie.
Defekt: statystyki nie są czyszczone po zakończeniu transferu. (odpowiednik BUG-3)
T-016
Starting traffic with negative Mbps is rejected
transfer.robot · obszar: walidacja brzegowa
Oczekiwane: błąd — przepustowość Mbps = -1 jest wartością ujemną, spoza dozwolonego zakresu.
Otrzymano: HTTP 200 — API akceptuje ujemną przepustowość.
Defekt: brak walidacji dolnej granicy przepustowości.
T-017
Starting traffic with extremely large Mbps is rejected
transfer.robot · obszar: walidacja brzegowa
Oczekiwane: błąd — Mbps = 1e9 (1 Pbps) jest wartością fizycznie nieosiągalną w sieciach LTE/5G.
Otrzymano: HTTP 200 — API akceptuje absurdalnie dużą wartość.
Defekt: brak walidacji górnej granicy przepustowości.
T-058
Starting traffic above the 100 Mbps DL limit is rejected
transfer.robot · obszar: spec ↔ implementacja
Oczekiwane: błąd — wg spec maksymalny transfer DL dla UE to 100 Mbps, a test używa Mbps = 101 (tuż powyżej limitu).
Otrzymano: HTTP 200 — API akceptuje 101 Mbps.
Defekt: deklarowany limit 100 Mbps nie jest egzekwowany. (odpowiednik BUG-13)
REGRESJA DEFEKTÓW — bugReports.robot

8 testów regresji bugów

Odwrócona logika: każdy test PRZECHODZI gdy błąd istnieje, a zafailuje, gdy zostanie naprawiony. Format: Błąd (stan obecny) → Poprawne zachowanie.

Cel: utrwalić defekt jako dowód i automatyczny sygnał naprawy. Wszystkie 8 = PASS.

BUG-1
Stop traffic zwraca sukces, gdy nie było aktywnego transferu
bugReports.robot · stop-transfer
Błąd: DELETE …/traffic na bearerze bez uruchomionego transferu zwraca traffic_stopped zamiast błędu.
Poprawnie: API powinno zwrócić 4xx — nie można zatrzymać sesji, która nigdy nie wystartowała.
Status testu: PASS — potwierdza obecność buga.
BUG-2
GET stats zwraca 200 dla bearera bez historii transferu
bugReports.robot · check-transfer
Błąd: odczyt transferu bearera, który nigdy nie miał sesji, zwraca 200 z pustymi polami (null, 0).
Poprawnie: API powinno zwrócić 404 — brak danych transferu dla tego bearera.
Status testu: PASS — potwierdza obecność buga.
BUG-3
GET stats zachowuje stare dane po zatrzymaniu transferu
bugReports.robot · check-transfer
Błąd: po stopie GET /traffic nadal zwraca historyczne protocol i target_bps z poprzedniej sesji.
Poprawnie: po stopie protocol i target_bps powinny być null, a tx_bps/rx_bps wyzerowane.
Status testu: PASS · powiązany NOK: T-036
BUG-4
Attach z ue_id = boolean true akceptowany jako UE 1
bugReports.robot · attach / walidacja
Błąd: pole ue_id akceptuje true, które Pydantic po cichu konwertuje na liczbę 1 i tworzy UE.
Poprawnie: API powinno zwrócić 422 — wartości boolowskie nie są poprawnymi identyfikatorami.
Status testu: PASS · powiązany NOK: T-077
BUG-5
bearer_count liczy aktywne transfery, nie skonfigurowane bearery
bugReports.robot · statystyki
Błąd: bearer_count w /ues/stats liczy bearery z aktywnym ruchem; dla UE z 2 bearerami bez ruchu daje 0.
Poprawnie: bearer_count powinien zliczać wszystkie skonfigurowane bearery.
Status testu: PASS · powiązany NOK: T-078
BUG-8
Usunięcie bearera z aktywnym ruchem zwraca sukces bez ostrzeżenia
bugReports.robot · integralność stanu
Błąd: DELETE …/bearers/{id} na bearerze z aktywną sesją zwraca bearer_deleted bez informacji o przerwaniu ruchu.
Poprawnie: API powinno zwrócić błąd (wymóg wcześniejszego stopu) lub jawnie potwierdzić zakończenie sesji.
Status testu: PASS · powiązany NOK: T-067
BUG-10
duration akumuluje się między kolejnymi sesjami na tym samym bearerze
bugReports.robot · statystyki / czas
Błąd: duration nie jest resetowane przy ponownym starcie — sumuje czas wszystkich poprzednich sesji na bearerze.
Poprawnie: duration powinno mierzyć tylko bieżącą sesję, zerując się przy każdym starcie.
Status testu: PASS · powiązany NOK: T-079
BUG-13
Limit 100 Mbps nie jest egzekwowany — dowolna wartość akceptowana
bugReports.robot · spec ↔ implementacja
Błąd: limit 100 Mbps ze spec nie działa — Mbps=10000 (10 Gbps) jest akceptowane; walidacja górnej granicy nieobecna.
Poprawnie: wartość powyżej 100 Mbps powinna zostać odrzucona.
Status testu: PASS · powiązany NOK: T-058
OBCIĄŻENIE I BEZPIECZEŃSTWO — stressTests.robot

6 testów stresowych

Testy niefunkcjonalne: wydajność i odporność na nadużycie zasobów (DoS). Format: Działanie → Wniosek / wykryta słabość.

Wszystkie 6 = PASS — potwierdzają brak mechanizmów ochronnych.

ST-001
Brak rate limitingu — burst 50 żądań /reset
stressTests.robot · DoS / rate-limit
Działanie: 50 kolejnych żądań POST /reset bez żadnej przerwy.
Wniosek: wszystkie 50 zwracają 200 — serwer nie ma throttlingu. Udokumentowany wektor DoS.
ST-002
Brak limitu rozmiaru żądania — payload 10 MB
stressTests.robot · DoS / payload
Działanie: POST /ues z dodatkowym polem o rozmiarze ~10 MB.
Wniosek: serwer przetwarza cały payload bez błędu — brak limitu rozmiaru na wejściu (wektor OOM).
ST-003
Brak limitu rozmiaru żądania — payload 100 MB
stressTests.robot · DoS / payload
Działanie: POST /ues z polem o rozmiarze ~100 MB.
Wniosek: serwer odpowiada bez błędu 5xx — pojedyncze żądanie potrafi wyczerpać pamięć bez limitu.
ST-004
Przepustowość attach — seryjne podłączenie 100 UE
stressTests.robot · wydajność
Działanie: kolejne podłączenie 100 unikalnych UE (ID 1–100) z pomiarem łącznego czasu.
Wniosek: wyznacza bazową przepustowość POST /ues i pozwala wykryć degradację wydajności.
ST-005
Reset pod pełnym obciążeniem — 100 UE w stanie
stressTests.robot · wydajność / stan
Działanie: po attach 100 UE wykonuje POST /reset i weryfikuje pełne wyczyszczenie stanu.
Wniosek: potwierdza, że reset czyści cały stan, oraz mierzy czas resetu przy pełnym obciążeniu.
ST-006
Crash test — payload 500 MB powoduje OOM w kontenerze
stressTests.robot · DoS / crash
Działanie: POST /ues z polem padding ~500 MB.
Wniosek: awaria kontenera (OOM) — brak jakiegokolwiek limitu rozmiaru żądania. Najpoważniejszy wektor DoS.
⚠️ Może pozostawić kontener niedostępnym — uruchamiać ostrożnie.
CZĘŚĆ B — co wyróżnia projekt

Rzeczy nieoczywiste

Decyzje projektowe i odkrycia, które wykraczają poza „napisać kilka testów”.

1

Każdy defekt udokumentowany dwukrotnie

Ten sam bug istnieje w dwóch testach o przeciwnej logice:

BugTest funkcjonalny (oczekuje POPRAWY)Test regresji (utrwala STAN OBECNY)

Po naprawie API test BUG-x zafailuje → automatyczny sygnał „defekt zniknął, zaktualizuj testy”.

2

Rozjazd specyfikacja ↔ implementacja

Część defektów to nie błędne wartości, lecz brakująca lub niezgodna funkcjonalność:

  • T-035 — spec przewiduje masowy stop DELETE /ues/{id}/traffic; endpointu brak w API → 404. Test poprawny, brak w implementacji.
  • T-058 / BUG-13 — dokumentacja deklaruje limit 100 Mbps DL; API przyjmuje dowolną wartość → limit nieegzekwowany.

Wniosek testerski: testy weryfikują zgodność z kontraktem, a nie tylko „czy nie wyrzuca wyjątku”. Wykrywają luki między dokumentacją a kodem.

3

Walidacja typów i wartości brzegowych

Analiza wartości brzegowych — testy „tuż za” granicą:

  • bearer 0 i 10 (zakres 1–9)
  • UE -1, 0, 100 (zakres 0–100)
  • Mbps ujemne / ekstremalnie duże

Pułapki typów wykryte i przetestowane:

  • ue_id: true → Pydantic po cichu robi 1 (BUG-4)
  • klucze bearerów w JSON to stringi
  • boolean/null jako wartości, nie napisy

Znajomość źródła błędu: walidacja zakresu = 422 z Pydantic, a nie ręczne 400 — to świadome rozróżnienie warstw.

4

5

Testy stresowe = wykrywanie podatności

stressTests.robot dokumentuje wektory DoS — to już testowanie niefunkcjonalne/bezpieczeństwa:

TestWykryta słabość
ST-001brak rate limitingu — 50 żądań /reset bez throttlingu
ST-002/003brak limitu rozmiaru żądania — payload 10 MB i 100 MB przyjęte
ST-006crash: payload 500 MB → OOM w kontenerze

Wniosek: serwer nie ma ochrony przed nadużyciem zasobów — realne ryzyko w środowisku produkcyjnym.

6

Powtarzalność i izolacja środowiska

  • Wersjonowany obraz epc-simulator:1.0.0 w Dockerze — każdy uruchamia identyczny SUT, niezależnie od maszyny.
  • Test Setup → /reset przed każdym testem — brak „wycieku” stanu między testami, brak zależności od kolejności.
  • Wynik 67/13 jest odtwarzalny — porównany między oryginalnym przebiegiem zespołu a ponownym uruchomieniem.

To fundament wiarygodności: test jest dowodem tylko wtedy, gdy daje ten sam wynik za każdym razem.
