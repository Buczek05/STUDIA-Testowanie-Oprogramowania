Testy T-009 – T-028

EPC Simulator · Robot Framework · transfer.robot + check_transfer.robot

⚠ Wykryte błędy — 4 testy FAIL (wynik z output.xml z 29.05.2026)
T-016 FAIL Ujemne Mbps (-1) powinno być odrzucone — ale API zaakceptowało

Co się stało: serwer zwrócił HTTP 200 z body {"status":"traffic_started", ..., "target_bps": -1000000} zamiast błędu 4xx.

Błąd w implementacji: endpoint POST /ues/50/bearers/9/traffic nie waliduje znaku wartości Mbps — ujemna szybkość jest traktowana jako poprawna i mnożona przez 10⁶, co daje target_bps = -1 000 000. Fizycznie niemożliwe.

T-017 FAIL Ekstremalnie duże Mbps (10⁹) powinno być odrzucone — ale API zaakceptowało

Co się stało: serwer zwrócił HTTP 200 z body {"target_bps": 1000000000000000} (10¹⁵ bps = 1 Pbps) zamiast błędu 4xx.

Błąd w implementacji: brak górnej granicy walidacji Mbps. Spec mówi, że maksymalny DL to 100 Mbps — serwer w ogóle nie sprawdza czy wartość mieści się w zakresie (1–100), akceptuje dowolną dodatnią liczbę.

T-027 FAIL Odpowiedź powinna zawierać total_tx_kbps — ale zawiera total_tx_bps

Co się stało: wywołano GET /ues/stats?ue_id=50&unit=kbps, serwer zwrócił HTTP 200, ale w body zamiast pól total_tx_kbps / total_rx_kbps zwrócił total_tx_bps / total_rx_bps z wartościami w bps (np. 10 253 016 524).

Błąd w implementacji: parametr unit jest ignorowany — serwer zawsze zwraca wartości w bps niezależnie od żądanej jednostki. Spec wymaga przeliczenia wartości i odpowiedniego nazewnictwa pól w odpowiedzi.

T-028 FAIL Nieaktywny bearer (5) powinien zwrócić błąd — ale API zwróciło 200

Co się stało: zapytanie GET /ues/50/bearers/5/traffic (bearer 5 nigdy nie był ustanowiony) zwróciło HTTP 200 z pustymi wartościami: {"protocol":null, "target_bps":null, "tx_bps":0, "rx_bps":0, "duration":0.0}.

Błąd w implementacji: serwer tworzy/zwraca "pusty" rekord statystyk nawet dla bearera, który nie ma żadnej historii transferu. Powinien zwrócić 404 lub inny błąd 4xx gdy bearer nie istnieje lub nigdy nie miał ruchu.

Podsumowanie zestawu testów

Zestaw obejmuje 20 testów podzielonych na dwa pliki: transfer.robot (T-009–T-020) testuje endpoint POST /ues/{ue_id}/bearers/{bearer_id}/traffic odpowiedzialny za uruchamianie transferu danych DL, natomiast check_transfer.robot (T-021–T-028) testuje odczyt statystyk przez GET /ues/{ue_id}/bearers/{bearer_id}/traffic i GET /ues/stats. Spośród 20 testów 4 są ścieżkami pozytywnymi (oczekiwany HTTP 200), a 16 sprawdza odrzucanie nieprawidłowych żądań (oczekiwany HTTP ≥ 400) — obejmując walidację zakresu szybkości (0, ujemne, 10⁹ Mbps), zakresu bearer ID (0 i 10, poprawny to 1–9), brakujących lub nadmiarowych pól, nieistniejących zasobów (UE, bearer) oraz konfliktów stanu (podwójny start). Każdy test zaczyna się od resetu EPC (POST /reset), co gwarantuje pełną izolację między przypadkami testowymi.

Typy testów: happy-path — ścieżka pozytywna, poprawne dane validation — walidacja wejścia error — obsługa błędnych stanów systemu stats — sprawdzenie statystyk ruchu ▶ kliknij kartę, aby rozwinąć szczegóły
